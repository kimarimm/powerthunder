# Архитектура веб-приложения «Файловое хранилище»

## 1. Анализ предметной области

**Предметная область:** Веб-приложение для хранения и обмена файлами между пользователями.

**Основные сущности:**
- **Пользователь** — регистрация, аутентификация, владение файлами
- **Файл** — загрузка, скачивание, метаданные (имя, размер, тип)
- **Общий доступ** — шаринг файлов между пользователями с заданными правами

**Функциональные требования:**
- Регистрация и вход
- Загрузка и скачивание файлов
- Просмотр списка файлов (свои + расшаренные)
- Удаление своих файлов
- Обмен файлами (share) с другими пользователями

---

## 2. Обоснование выбора технологий

| Компонент | Выбор | Обоснование |
|-----------|-------|-------------|
| Язык | Python | Требование задания; развитая экосистема для веб-разработки |
| Фреймворк | FastAPI | Современный async, автоматическая документация OpenAPI, валидация Pydantic |
| БД | SQLite + SQLAlchemy | Простота развёртывания; лёгкая миграция на PostgreSQL при необходимости |
| Аутентификация | JWT + bcrypt | Стандарт для REST API, stateless |
| Паттерн | Clean Architecture | Разделение слоёв, тестируемость, независимость от фреймворка |
| Фронтенд | Vanilla JS, HTML5, CSS3 | Соответствие современным стандартам, без тяжёлых зависимостей |
| Развёртывание | Docker, Docker Compose | Воспроизводимое окружение, изоляция процесса от хост-системы |
| CI/CD | GitHub Actions | Автоматический деплой на сервер по SSH при пуше в `master` |

---

## 3. Архитектура (Clean Architecture)

```
┌─────────────────────────────────────────────────────────────┐
│                    PRESENTATION (API, Web)                  │
│  Маршруты FastAPI, схемы Pydantic, статические страницы     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    APPLICATION (Use Cases)                  │
│  AuthService, UserService, FileService                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    DOMAIN (Entities, Ports)                 │
│  User, File, FileShare | IUserRepository, IFileRepository   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    INFRASTRUCTURE (Adapters)                │
│ UserRepository, FileRepository, LocalFileStorage, SQLAlchemy│
└─────────────────────────────────────────────────────────────┘
```

**Принципы:**
- Зависимости направлены внутрь (к домену)
- Домен не зависит от фреймворков и БД
- Бизнес-логика изолирована в application-слое

---

## 4. Слой серверной логики

- **AuthService** — хеширование паролей, JWT
- **UserService** — регистрация, получение пользователя
- **FileService** — загрузка, скачивание, удаление, шаринг

---

## 5. Слой базы данных

- **Модели:** UserModel, FileModel, FileShareModel (SQLAlchemy ORM)
- **Репозитории:** UserRepository, FileRepository — реализация портов домена
- **Файловое хранилище:** LocalFileStorage — сохранение файлов на диск

---

## 6. Слой представления

- **REST API:** `/api/auth/*`, `/api/files/*`
- **SPA:** index.html, app.js — маршрутизация по hash (#/login, #/files, #/upload)
- **Межстраничная навигация:** реализована на клиенте (hash routing)

---

## 7. Развёртывание

- **Docker:** многоступенчатый `Dockerfile` — сборка зависимостей в отдельном слое, минимальный рантайм-образ, непривилегированный пользователь
- **Docker Compose:** `docker-compose.yml` — контейнер приложения, том для БД и загруженных файлов
- **CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`) — при пуше в `master` копирует проект на сервер и выполняет `docker compose up -d --build`
